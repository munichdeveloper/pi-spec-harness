PI-SPEC-HARNESS – QUICK REFERENCE
=================================

KANONISCHER ABLAUF

  approved Spec auf Default-Branch
    -> spec-to-issue erzeugt dedupliziert ein Implementierungs-Issue
    -> Mensch setzt genau ein Label: harness:approved-for-agent
    -> Label-Bündelung ergänzt status:ready, ai:allowed,
       harness:implementation
    -> deterministischer Run issue-<issue-number> entsteht
    -> Delivery-PR gegen main
    -> Coding-Agent-PR gegen den Delivery-Branch
    -> CI, Review und höchstens drei automatische Iterationen
    -> Implementation-PR in Delivery-Branch
    -> SHA-spezifisches Human-Gate für Medium-/High-Risk-Delivery-Merge
    -> nachgewiesener Merge-Effekt
    -> Run complete

WAHRHEITSQUELLE

  Genau ein offenes Tracking-Issue [Harness Run] <run-id> mit
  harness:run. Sein Body enthält den kanonischen State. Chat, lokale
  Dateien und Suchen nach der "neuesten" Ressource sind keine State-Quelle.

HUMAN GATES

  offen:      harness:gate-open + status:needs-human
  freigeben:  harness:gate-approved
  ablehnen:   harness:gate-rejected

  Kommentare oder Chat-Aussagen zählen nicht als Entscheidung.

WICHTIGE BEFEHLE

  npm run harness -- status \
    --repository owner/repo --run-id <run-id>

  npm run harness -- resume \
    --repository owner/repo --run-id <run-id>

  npm run harness -- orchestrate \
    --repository owner/repo --run-id <run-id>

  npm run harness -- delivery-pr-bind \
    --repository owner/repo --run-id <run-id> \
    --pull-request <number> --head-sha <full-40-char-sha>

  npm run harness -- impl-pr-bind \
    --repository owner/repo --run-id <run-id> \
    --pull-request <number> --head-sha <full-40-char-sha> \
    --expected-base <delivery-branch>

INSTALLATION IN EIN ZIELREPOSITORY

  Einen existierenden, unveränderlichen Release-Tag oder vollständigen SHA
  verwenden; niemals einen erfundenen oder noch nicht veröffentlichten Ref.

  npm run harness -- init \
    --repository owner/repo --run-id bootstrap-001 \
    --requirement REQ-001 --spec SPEC-001 \
    --install-workflows bug-triage,spec-to-issue,label-approval-bundling \
    --workflow-ref <release-tag-or-full-sha> \
    --install-agents-context

  Installierte Dateien sind markiert. Ergebnis:
    create          neue Referenz angelegt
    noop            bereits byteidentisch
    update-managed  ausschließlich verwaltete Datei aktualisiert
    conflict        nicht verwaltete Datei bleibt unangetastet

  Bestehende Repositories werden nie automatisch migriert.

SICHERHEITSREGELN

  - Nie "latest", tail -1 oder --limit 1 zur Ressourcenauswahl nutzen.
  - PR-Nummer und vollständigen HEAD-SHA im Run-State binden.
  - Neuer SHA invalidiert alte Review-/Gate-Evidence.
  - Coding-Agent-PR zielt auf den Delivery-Branch, nicht auf main.
  - Medium-/High-Risk-Merge benötigt ein SHA-spezifisches Human-Gate.
  - Gate-Erfolg ist nicht Merge-Erfolg; complete erst nach Merge-Nachweis.
  - Nach drei fehlgeschlagenen Iterationen stoppen und eskalieren.
  - Recovery ausschließlich unter recovery/*; niemals direkt nach main.
  - Keine Secrets oder echten Nutzer-/Produktionsdaten im State/Evidence.
