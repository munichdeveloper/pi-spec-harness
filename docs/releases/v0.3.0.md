# pi-spec-harness v0.3.0

Status: Release-Kandidat  
Vorbereitet: 2026-08-26

Der Tag `v0.3.0` wird erst erstellt, nachdem Clean-Install, Upgrade,
Capability-Smoke und die dokumentierte Post-Install-Verifikation erfolgreich
abgeschlossen wurden. Bis dahin ist dieses Dokument eine überprüfbare
Release-Kandidatenbeschreibung, keine Behauptung einer Veröffentlichung.

## Highlights

- Evidenzbasierte Phaseninvarianten verhindern, dass ein Run ohne aktuelle
  Implementierungs-, Review- und Verifikationsevidenz bis zum Merge gelangt.
- Deterministische Legacy-Recovery führt ungültige Altzustände auf die früheste
  belegbare Phase zurück und bewahrt die append-only Historie.
- Gate-Supersession ersetzt überholte Entscheidungen explizit und auditiert,
  statt widersprüchliche Gates parallel wirksam zu lassen.
- Requirements können durch einen konfigurierbaren Agenten in Software-Specs
  überführt und mit einer einzigen menschlichen Freigabe weitergereicht werden.
- Vertrauenswürdige Review-Findings können gebunden an PR und Head-SHA in den
  bestehenden Run zurückgeführt und automatisch remediated werden.
- Prozess-Audit-Ereignisse werden idempotent, validiert und konfliktfest im
  kanonischen Journal persistiert.
- Die Installation der Freigabe-Label-Bündelung provisioniert Trigger- und
  Ziellabels idempotent, bevor der Workflow aktiviert wird.
- Alle installierbaren Workflow-Templates verwenden denselben existierenden,
  unveränderlichen vollständigen SHA statt `main`, zukünftiger Tags oder
  uneinheitlicher Altversionen.

## Enthaltene Stabilitätskorrekturen

- #110: Relevante Default-Branch-Pushes werden auf einen unterstützten
  `workflow_dispatch` gebridged; Feature-Branch-Pushes starten keinen
  kostenpflichtigen Capability-Smoke
- #108: Capability-Smoke-Caller und Reusable gewähren der fest gepinnten
  Claude-Action die erforderliche, kurzlebige OIDC-Token-Berechtigung, ohne
  Repository-, Issue-, PR- oder Deployment-Schreibrechte zu eröffnen
- #106: Capability-Smoke-Caller delegiert die Serialisierung ausschließlich an
  den wiederverwendbaren Workflow und vermeidet verschachtelte GitHub-
  Concurrency-Deadlocks
- #84 / PR #101: evidenzbasierte Phaseninvarianten und Legacy-Recovery
- #58 / PR #102: vollständige, idempotente Label-Provisionierung
- PR #103: konsistente immutable Workflow-Referenzen für Katalog und
  selbst installierte Harness-Caller
- #96 / PRs #97–#98: zuverlässiger Self-Finalizer ohne verschachtelten
  Concurrency-Deadlock

## Installation nach Veröffentlichung

```bash
pi install git:github.com/munichdeveloper/pi-spec-harness@v0.3.0
```

Workflow-Caller können explizit auf `v0.3.0` gesetzt werden. Ohne expliziten
`--workflow-ref` verwendet der Installer den im Release verifizierten
vollständigen SHA.

## Upgrade-Hinweise

- Verwaltete Workflow-Dateien werden idempotent aktualisiert.
- Nicht verwaltete Dateien werden nicht überschrieben und als Konflikt
  gemeldet.
- Projektspezifische Konfiguration und bestehende Audit-Journale müssen beim
  Upgrade unverändert erhalten bleiben; dies ist ein eigenes Release-Gate.
- Das Freigabe-Label `harness:approved-for-agent` sowie die konfigurierten
  Ziellabels werden bei Bedarf angelegt. Bestehende Label-Metadaten bleiben
  erhalten.

## Verifikation vor Tag-Erstellung

- verpflichtendes CI-Gate `npm run release:smoke` mit vollständigem
  `npm run check` und Build
- Packen des tatsächlich zu veröffentlichenden npm-Artefakts und Prüfung der
  erforderlichen Runtime-Dateien
- Clean-Install dieses Artefakts in einem leeren temporären Testprojekt mit
  erfolgreichem Start der installierten CLI
- idempotente Neuinstallation als Upgrade-Smoke; bestehende
  Projektkonfiguration und Audit-Historie bleiben dabei bytegenau erhalten
- Capability-Smoke und relevante synthetische E2E-Pfade
- Prüfung, dass alle Workflow-Refs erreichbar und unveränderlich sind
- bestätigte Audit- und Post-Install-Evidenz

## Bekannte Abgrenzung

Die weitergehende autonome Review-Recovery aus #72 und die konkrete
Wiederherstellung aus #85 sind nicht Teil dieses Releases, sofern ihre offenen
Punkte keinen oben beschriebenen Stabilitätsvertrag verletzen.
