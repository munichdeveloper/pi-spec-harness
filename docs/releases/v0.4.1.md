# pi-spec-harness v0.4.1

Status: Release-Kandidat
Vorbereitet: 2026-08-31

Der Tag `v0.4.1` und der GitHub Release werden erst nach grünem Release-PR,
Post-Merge-CI, Release-Smoke und bestätigtem Release-Audit erstellt.

## Änderung

Der optionale `requirement-to-spec`-Workflow unterstützt nun ein pro
Zielrepository konfigurierbares Spec-Zielverzeichnis. Damit kann Immogent
Requirements aus `docs/20-requirements/**/*.md` beobachten und Specs unter
`docs/30-specifications` erzeugen, ohne seine Vault-Struktur zu verändern.

Die neue Option wird durch Installer, Managed Caller, reusable Workflow, CLI
und providerneutrale Dispatch-Order unverändert gebunden. Der bestehende Default
`docs/specifications` bleibt rückwärtskompatibel.

## Sicherheit

Das Zielverzeichnis wird vor dem Schreiben des Managed Workflow-YAML und erneut
vor Provider-Dispatch fail-closed validiert. Absolute Windows-, POSIX- und
UNC-Pfade, Traversal, Dot-/Leersegmente, Backslashes, Whitespace,
Abschluss-Slashes, Steuerzeichen sowie YAML-relevante Quote-Zeichen werden
abgelehnt.

## Installation nach Veröffentlichung

```bash
pi install git:github.com/munichdeveloper/pi-spec-harness@v0.4.1
```

Beispiel für Immogent:

```bash
harness init \
  --install-workflows requirement-to-spec \
  --workflow-ref 60353584d46b00f72c617d8f76eefaa4b333eaac \
  --requirement-path-glob 'docs/20-requirements/**/*.md' \
  --requirement-spec-output-dir 'docs/30-specifications' \
  --requirement-provider github-copilot
```

Bestehende Requirements werden nicht rückwirkend verarbeitet. Der Merge eines
generierten Spec-PRs bleibt die einzige Spec-Freigabe; ein zusätzliches
Approval-Label ist nicht erforderlich.
