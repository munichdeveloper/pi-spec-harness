# pi-spec-harness v0.4.0

Status: Release-Kandidat
Vorbereitet: 2026-08-29

Der Tag `v0.4.0` und der GitHub Release werden erst nach grünem Release-PR,
Post-Merge-CI, Clean-Install/Upgrade-Smoke und bestätigtem Release-Audit erstellt.

## Highlights

- Strukturierte Readiness wird getrennt von fachlicher Spec-Freigabe bewertet.
- Technische Blocker können als begrenzte, revisionsgebundene Spikes auf dem
  kanonischen Run ausgeführt und unabhängig verifiziert werden.
- Controller und Executor sind an Repository, Workflow, Runtime-SHA, Spec-Blob,
  Receipt, Actor und Actions-Versuch gebunden.
- Scheduler und Completion-Events setzen Runs idempotent fort; verpasste Events,
  temporär fehlende Kapazität und Abbruch vor dem Claim werden ohne doppelte
  Agent-Ausführung wiederhergestellt.
- Veraltete oder falsch gebundene Evidence wird vor der Implementierung abgelehnt.
- Synthetische Nachweise können evidenzerhaltend disponiert werden: Child-Issues
  werden geschlossen, Tracking-Run, Phase, Work Records und Audit bleiben erhalten.
- Audit-Bestätigung nutzt indizierte Kandidaten mit sicherem vollständigem Fallback.

## Installation nach Veröffentlichung

```bash
pi install git:github.com/munichdeveloper/pi-spec-harness@v0.4.0
```

Ohne expliziten `--workflow-ref` verwendet der Installer weiterhin den oben
genannten unveränderlichen, release-verifizierten Commit-SHA.

## Upgrade von v0.3.0

- Verwaltete Workflow-Caller werden idempotent auf den v0.4.0-SHA aktualisiert.
- Nicht verwaltete Dateien, Produktkonfiguration und bestehende Audit-Journale
  werden nicht überschrieben.
- Bestehende Runs werden nicht rückwirkend als vollständig markiert.
- Readiness-Automation bleibt nach Installation deaktiviert, bis ein Zielrepo
  seine explizite Runtime-/Executor-Konfiguration gesetzt hat.

## Abgrenzung

- Die Nachweise verwenden ausschließlich deterministische synthetische Agenten
  im 0-Euro-Rahmen; sie belegen keine reale Copilot-/Claude-Codequalität.
- Der konfliktbehaftete historische PR #81 und seine Recovery-Issues #70/#80/#85
  sind nicht Teil dieses Releases. Sie werden nicht stillschweigend integriert.
- Es werden keine Immogent-Produktänderungen, kostenpflichtigen Ressourcen oder
  produktiven Provider durch diesen Release aktiviert.
